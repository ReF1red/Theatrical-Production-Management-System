# Система управления театральными постановками

Учебный проект ПР1–ПР7: репертуар, готовность спектаклей, подбор актёров,
показы, билеты и бронирования. Консольная версия работает с JSON;
сайт на Django использует шаблоны и по умолчанию читает SQLite через `sqlite3`.
Django ORM и миграции не используются.

Нужен Python 3.10 или новее.

## Установка и запуск ПР7

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m db.import_json
python manage.py runserver
```

Команда импорта нужна, если `data/theatre.sqlite` ещё не заполнена.
В рабочей папке уже подготовлена база с исходными данными: 2 постановки,
3 актёра, 2 роли, 2 показа и 1 бронь. Старый файл `data/theatre.sqlite3`
из предыдущих работ сохраняется отдельно и сайтом ПР7 не используется.

Сайт: [http://127.0.0.1:8000/](http://127.0.0.1:8000/).

Повторный импорт в заполненную базу отклоняется. Чтобы явно заменить данные
SQLite текущим содержимым JSON, выполните:

```bash
python -m db.import_json --replace
```

Это заменяет содержимое пяти таблиц ПР7 в одной транзакции. При ошибке
импорт откатывается. JSON не изменяется. Произвольные пути можно передать
через `--data-dir` и `--database`.

## Режим ПР6 и консоль

ПР6 демонстрирует шаблоны с исходными объектами и JSON-хранилищем:

```bash
THEATRE_DATA_SOURCE=json python manage.py runserver
```

Основные страницы, фильтр жанра и поиск свободных показов доступны в обоих
режимах. Статистика по постановкам и залам добавлена в ПР7 для SQLite.
Для другого файла базы задайте `THEATRE_SQLITE_PATH=/путь/к/базе.sqlite`.

Консольная версия сохранена:

```bash
python main.py
```

Добавлять и изменять данные можно через консоль. После таких изменений
повторите импорт с `--replace`, чтобы обновить сайт ПР7.
Сайт поддерживает GET и HEAD и не изменяет хранилища.

## Страницы и сценарии

| Адрес | Назначение |
| --- | --- |
| `/` | Главная, счётчики, ближайшие показы, репертуар |
| `/productions/` | Постановки, фильтрация по жанру `?genre=комедия` |
| `/productions/1/` | Карточка постановки, готовность, показы и подбор актёров |
| `/shows/` | Расписание с количеством свободных мест |
| `/shows/1/` | Карточка показа и ссылки на постановку и брони |
| `/bookings/` | История броней и показатели продаж |
| `/bookings/?status=active` | Активные бронирования |
| `/bookings/?status=cancelled` | Отменённые бронирования |
| `/bookings/1/` | Билет, постановка, дата, зал, цена и статус |
| `/shows/available/?date=2026-10-20` | Поиск показов со свободными местами на дату |
| `/statistics/` | Статистика по постановкам и залам, фильтр `?threshold=0` |

Для исходного показа 20.10.2026 свободно 119 из 120 мест.
Показ 25.11.2026 имеет 120 свободных мест. Поиск разрешает и прошлые даты,
чтобы можно было проверить исходный набор данных. На главной странице
раздел ближайших показов учитывает текущую дату.
Отмена брони сохраняет запись и освобождает место; в выручку отмены не входят.
Ошибочный идентификатор даёт 404, неверный параметр даты или статуса — 400,
недоступное/повреждённое хранилище — 503 без раскрытия технических деталей.

## ПР6 — шаблоны и статика

- `templates/base.html` — общий документ, блоки `title` и `content`.
- `templates/includes/` — навигация, карточка постановки, статус, расписание.
- `templates/homepage/`, `repertoire/`, `performances/`, `reservations/` —
  наследуемые шаблоны всех страниц.
- Во views используется `render(request, template, context)`. Формирование
  HTML в Python и вызовы старой `page()` устранены.
- Используются `extends`, `block`, `include`, `for/empty`, `if`, `with`,
  именованные URL и пространства имён приложений.
- Фильтры: `date`, `floatformat`, `length`, `default`, `capfirst`, `join`, `yesno`.
- `homepage/static/homepage/` — собственный CSS, SVG-изображение и JavaScript
  для кнопки возврата наверх. Подключение — через `{% static %}`.
- Автоматическое экранирование пользовательских данных сохранено.

## ПР7 — база данных

Схема: `sql/schema.sql`, база: `data/theatre.sqlite`.
Все сущности текущих JSON-файлов перенесены в отдельные таблицы.
Билет остаётся объектом внутри брони; его зона, категория и цена — поля `bookings`.

| Таблица | Поля и связи |
| --- | --- |
| `productions` | `id INTEGER PRIMARY KEY`, `title`, `author`, `genre`, `premiere_date TEXT`, три признака готовности `INTEGER` |
| `actors` | `id INTEGER PRIMARY KEY`, `name`, `gender TEXT`, `age INTEGER` |
| `roles` | `id INTEGER PRIMARY KEY`, `production_id` → `productions`, `title`, `required_gender TEXT`, `min_age`, `max_age INTEGER` |
| `shows` | `id INTEGER PRIMARY KEY`, `production_id` → `productions`, `datetime TEXT`, `hall TEXT`, `capacity INTEGER` |
| `bookings` | `id INTEGER PRIMARY KEY`, `show_id` → `shows`, `seat_number`, `zone INTEGER`, `category TEXT`, `price REAL`, `is_cancelled INTEGER` |

Даты хранятся в ISO-формате, логические значения — как 0/1. Все поля текущей
модели обязательны (`NOT NULL`; ключи `INTEGER PRIMARY KEY` задаются явно).
Отсутствие записей выражается пустой выборкой; `SUM`/`AVG` для пустой выборки
обрабатываются через `COALESCE`. Внешние ключи включаются на каждом подключении.
Ограничения `CHECK` контролируют значения, частичный уникальный индекс запрещает
две активные брони одного места, триггеры проверяют номер места при вставке
и изменении брони. Пара `(hall, datetime)` уникальна.

- `db/database.py` — `sqlite3.connect`, `sqlite3.Row`, включение внешних ключей,
  транзакции, закрытие подключений, загрузка именованных запросов.
- `db/import_json.py` — создание схемы, проверка исходных объектов, `executemany`,
  транзакционный импорт, проверка связей. Успех фиксируется `commit` контекстом
  соединения, ошибка вызывает `rollback`.
- `db/repository.py` — чтение строк по именам полей и восстановление прежних
  предметных классов; их методы готовности и подбора продолжают работать.
- `homepage/data.py` — выбор JSON или SQLite; сайт открывает SQLite только на чтение.

## SQL-запросы и их использование

Единый источник SQL — `sql/queries.sql`. Его 16 именованных блоков выполняются
без копирования SQL в представления. Все пользовательские значения передаются
параметрами `?`; имена таблиц в импорте берутся только из фиксированной схемы.

| № | Имя запроса | Вид и использование |
| --- | --- | --- |
| 1–5 | `productions`, `actors`, `roles`, `shows`, `bookings` | SELECT, ORDER BY; загрузка объектов для страниц |
| 6 | `productions_by_genre` | WHERE; фильтр репертуара |
| 7 | `bookings_by_status` | WHERE; фильтр броней |
| 8 | `schedule` | JOIN, COUNT, GROUP BY; расписание |
| 9 | `booking_detail` | JOIN, WHERE; зал в карточке брони |
| 10 | `counters` | COUNT; счётчики главной |
| 11 | `booking_statistics` | COUNT, SUM, AVG, COALESCE; брони и статистика |
| 12 | `production_statistics` | LEFT JOIN, GROUP BY; статистика постановок |
| 13 | `hall_statistics` | LEFT JOIN, GROUP BY; статистика залов |
| 14 | `popular_productions` | GROUP BY, HAVING; фильтр по числу броней |
| 15 | `available_shows` | WHERE, JOIN, GROUP BY, HAVING; свободные показы по дате |
| 16 | `suitable_actors` | JOIN, BETWEEN, WHERE; актёры для ролей постановки |

Проверка в SQLite CLI (`.schema`, `.tables`, `.parameter`, затем `.read`):

```bash
sqlite3 data/theatre.sqlite
```

Параметризованные блоки удобно выполнять отдельно; например:

```sql
.parameter init
.parameter set ?1 0
SELECT * FROM bookings WHERE is_cancelled = ?1 ORDER BY id DESC;
PRAGMA foreign_key_check;
PRAGMA integrity_check;
```

## Проверка проекта

```bash
python manage.py check
python -m pytest -v
python -m flake8 .
THEATRE_DATA_SOURCE=json python -m pytest -v --ignore=tests/test_sqlite.py
```

Тесты используют временные JSON-файлы и отдельные базы SQLite. Проверяются
обе версии хранения, страницы, наследование шаблонов и статика, экранирование,
импорт и откат, ключи, занятые места и отмены, SQL-фильтры, пустая база,
агрегаты, поиск по дате и ошибки. Исходные данные тесты не изменяют.

Отчёты: `docs/Отчет_ПР6.docx` и `docs/Отчет_ПР7.docx`.
Изменения ПР6 и ПР7 подготовлены без создания Git-коммитов.
